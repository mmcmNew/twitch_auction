# Предложение по реализации сервиса Twitch Auction

## 1) Краткая концепция

Сервис строится как веб-приложение из двух интерфейсов:
- **Панель стримера/модератора** (управление аукционами, модерацией, ролями, историей).
- **Интерфейс зрителя + OBS-виджет** (вложения баллов, просмотр рейтинга, live-обновления).

Ключевая модель голосования: зритель не выбирает один пункт, а **распределяет баланс** между несколькими позициями.

---

## 2) Предлагаемая архитектура

## Backend
- **Node.js + NestJS** (или Fastify/Express) для API и бизнес-логики.
- **PostgreSQL** как основная БД.
- **Redis** для кеша, rate limit и live-метрик.
- **WebSocket (Socket.IO / native ws)** для обновления таблицы в реальном времени.
- **BullMQ / очередь задач** для фоновых задач (синхронизация, отчёты, очистка).

## Frontend
- **React + Next.js**:
  - `/dashboard` — стример и модераторы.
  - `/viewer` — интерфейс зрителя.
  - `/overlay` — легковесный OBS-виджет.
- UI: Chakra UI / MUI + адаптивная таблица.

## Интеграция Twitch
- OAuth2 вход для стримера.
- Проверка ролей (streamer/moderator/viewer) через Twitch API.
- Интеграция с Channel Points через EventSub / PubSub (в зависимости от актуального API/доступа).

---

## 3) Доменные сущности (минимальный набор)

- **User**: `id`, `twitch_id`, `display_name`, `role`, `is_active`.
- **Auction**: `id`, `channel_id`, `title`, `status` (`draft|active|closed`), `started_at`, `ended_at`, `source_auction_id`.
- **Position**: `id`, `auction_id`, `title`, `normalized_title`, `status`, `created_by`, `is_merged`, `merged_to_id`.
- **Suggestion**: `id`, `auction_id`, `author_id`, `title`, `status` (`pending|approved|rejected`), `moderator_id`, `moderated_at`.
- **Wallet**: `id`, `auction_id`, `user_id`, `balance_total`, `balance_available`.
- **Contribution**: `id`, `auction_id`, `position_id`, `user_id`, `amount`, `created_at`.
- **AuctionSnapshot**: снимок итогов завершённого аукциона для быстрого просмотра истории.
- **AuditLog**: лог действий модерации/управления ролями.

---

## 4) Основные бизнес-правила

1. **Вложения только в рамках доступного баланса**.
2. **Новые предложения всегда проходят модерацию** до попадания в таблицу.
3. При объединении дубликатов все вложения переносятся на целевую позицию транзакционно.
4. Роли и критические действия (удаление, merge, смена прав) журналируются.
5. Любые операции с балансом и вложениями выполняются в БД-транзакциях.

---

## 5) API (черновой контракт)

### Auth
- `GET /auth/twitch/login`
- `GET /auth/twitch/callback`
- `GET /me`

### Аукционы
- `POST /auctions` — создать.
- `POST /auctions/:id/start` — запустить.
- `POST /auctions/:id/close` — завершить.
- `POST /auctions/:id/restart` — перезапуск из истории.
- `POST /auctions/:id/clone` — перенос в новый аукцион (с флагом переноса баллов/без).
- `GET /auctions` / `GET /auctions/:id`.

### Позиции и предложения
- `GET /auctions/:id/positions`
- `POST /auctions/:id/suggestions`
- `POST /suggestions/:id/approve`
- `POST /suggestions/:id/reject`
- `POST /positions/:id/merge`
- `PATCH /positions/:id`
- `DELETE /positions/:id`

### Баланс и вложения
- `GET /auctions/:id/wallet`
- `POST /auctions/:id/wallet/topup` (по событию Twitch или ручному тех. режиму)
- `POST /auctions/:id/contributions` (position_id + amount)
- `GET /auctions/:id/contributions/history`

### Роли и модерация
- `GET /roles`
- `POST /roles/assign`
- `POST /roles/revoke`
- `GET /audit-log`

### История и календарь
- `GET /history/auctions`
- `GET /history/auctions/:id`
- `GET /history/calendar`

---

## 6) Реализация ключевых требований

### Перенос аукционов
Добавить мастер «Создать новый аукцион на основе старого» с режимами:
1. **Carry-over full**: копировать позиции и текущие суммы.
2. **Carry-over list only**: копировать позиции, но обнулить суммы.
3. **Selective reset**: копировать всё и обнулить выбранные позиции.

Технически: `clone`-операция формирует новый `auction_id`, копирует позиции, затем (опционально) агрегированные суммы во `Contribution` и `AuctionSnapshot` стартового состояния.

### Календарь и история
- Индексированный список завершённых аукционов.
- Карточка аукциона: дата, победители, общий объём вложений, top-N позиций.
- Кнопка «Запустить снова» -> сценарий `restart/clone`.

---

## 7) Антиспам и качество данных

- Rate limit на создание предложений (например, N в час).
- Нормализация названий (`trim`, lowercase, удаление спецсимволов) и проверка похожести (Levenshtein/Jaro-Winkler) для подсказки дубликатов.
- Пороговые правила для новых пользователей (например, минимальный возраст подписки/аккаунта — опционально).
- Ограничение максимального вклада за операцию.

---

## 8) UX-потоки

### Для зрителя
1. Открыть страницу, увидеть баланс и топ позиций.
2. Предложить новую позицию (если нужно).
3. Внести баллы в 1–N позиций.
4. Мгновенно увидеть изменение ранга.

### Для стримера/модератора
1. Запустить аукцион.
2. Модерировать входящие предложения.
3. Объединять дубликаты и править названия.
4. Завершить аукцион, сохранить в историю.
5. При необходимости запустить следующий раунд на базе прошлого.

---

## 9) Безопасность и надёжность

- JWT + refresh токены, HttpOnly cookie.
- RBAC на уровне API.
- Идемпотентность критических эндпоинтов (`contribute`, `merge`).
- Транзакции + optimistic locking на конкурентных операциях.
- Метрики и алерты (ошибки API, лаг сокетов, аномальные всплески предложений).
- Ежедневные backup БД.

---

## 10) Метрики успеха (в BI/аналитике)

- DAU/MAU участников аукционов.
- Конверсия: «зашёл в аукцион» -> «внёс баллы».
- Средний вклад на пользователя.
- Доля предложений, прошедших модерацию.
- Retention по аукционам (повторное участие).
- Среднее время до модерации предложения.

## 11) План внедрения (MVP -> V2)

### MVP (4–6 недель)
- OAuth Twitch, роли, один активный аукцион.
- Позиции, предложения, модерация.
- Баланс и вложения.
- Live-таблица + OBS-виджет.
- Завершение аукциона и базовая история.

### V1.1
- Перенос/клонирование аукционов с частичным сбросом.
- Расширенный audit log и антиспам.
- Улучшенный дубликат-детектор.

### V2
- Сезонные рейтинги, командные режимы.
- Несколько параллельных аукционов.
- Глобальная аналитика канала.

---

## 12) Риски и меры снижения

- **Риск:** сложность интеграции Channel Points.  
  **Мера:** абстракция провайдера начислений + fallback ручного пополнения в раннем релизе.
- **Риск:** спам/троллинг предложениями.  
  **Мера:** rate limit, премодерация, доверенные роли.
- **Риск:** падение вовлечённости из-за сложного UI.  
  **Мера:** 1-экранный сценарий для зрителя, минимум действий.

---

## 13) Рекомендация по старту

Начать с **MVP на одном канале**, проверить продуктовые гипотезы (вовлечение, повторное участие, скорость модерации), затем расширять функциональность переноса и мультиаукционов. Это даст быстрый запуск и раннюю валидацию без избыточной сложности.

## 14) Frontend-стратегия: React + PWA + мобильная адаптация

### Рекомендуемый стек
- **Next.js (React)** как основной frontend.
- **TypeScript** для строгих контрактов с backend API.
- **TanStack Query** для кеширования и фоновой синхронизации.
- **Zustand/Redux Toolkit** для локального UI-state (фильтры, эффекты, текущая роль).
- **PWA-слой**: `next-pwa` + Workbox (service worker, offline cache, install prompt).

### PWA-цели
1. Установка на iOS/Android/desktop как «почти нативного» приложения.
2. Быстрый повторный запуск (кеш shell + статики).
3. Фоновое обновление данных и graceful-degradation при нестабильной сети.
4. Web Push (опционально): уведомления о старте/финале аукциона, смене лидера.

### Что кэшировать
- **Cache First**: статические assets (JS/CSS/fonts/icons).
- **Stale While Revalidate**: публичные read endpoint’ы (`positions`, `history`, `activity`).
- **Network First**: критические mutation endpoint’ы (`contributions`, `approve/reject`, `lock/roulette`).

### Мобильная адаптация (обязательно)
- Mobile-first layout, breakpoints: 360 / 390 / 768 / 1024.
- Sticky action bar снизу (внести баллы, открыть таблицу, предложить позицию).
- Компактный режим таблицы лотов + крупные touch targets.
- Сценарий «смотрю стрим + голосую» в одном экране:
  - встроенный плеер Twitch;
  - collapsible блок активности;
  - быстрый ввод суммы и подтверждение вклада.
- Оптимизация для слабых устройств: уменьшение анимаций и ограничение частоты перерисовок.

### UI-эффекты (событийная модель)
- `leader_changed` -> подсветка нового лидера.
- `large_contribution` -> анимация/баннер «крупный вклад».
- `auction_ending_soon` -> заметный таймер и warning-состояние.
- `new_vote_or_suggestion` -> мягкое уведомление в activity feed.

### План frontend-спринтов
1. **Sprint UI-1**: каркас страниц `/viewer`, `/dashboard`, `/overlay`, базовый дизайн-систем слой.
2. **Sprint UI-2**: activity feed + эффекты + таймер окончания + stream embed.
3. **Sprint UI-3**: PWA (manifest, service worker, offline shell, install flow).
4. **Sprint UI-4**: мобильная полировка, performance budget, accessibility pass.

## 15) Обновлённый план спринтов (от текущего состояния)

Ниже план с учётом уже реализованного backend MVP (роли, модерация, вклады, roulette/clone/restart, activity/effects/SSE) и фокуса на выход в production-ready MVP.

### Sprint A — Архитектурная стабилизация backend (1–2 недели)
**Цель:** снизить связность `main.py`, зафиксировать устойчивые доменные правила и тестируемость.

- Вынести в сервисный слой use-case блоки:
  - suggestions moderation flow;
  - contribution orchestration (wallet/position/audit/effects);
  - auction lifecycle orchestration (start/lock/roulette/close/restart).
- Ввести единый формат ошибок API (problem details / стабильные `code` + `message`).
- Добавить контрактные тесты на негативные сценарии переходов состояний.
- Подготовить миграции (Alembic) вместо `create_all` для управляемых обновлений схемы.

**Критерий готовности:**
- Роутеры в основном orchestration-only;
- ключевые правила покрыты unit-тестами сервисов;
- схема БД обновляется миграциями.

### Sprint B — UI Core (2 недели)
**Цель:** дать рабочий интерфейс viewer + dashboard + overlay.

- Next.js каркас страниц: `/viewer`, `/dashboard`, `/overlay`.
- Подключение backend API:
  - позиции/вклады/предложения;
  - activity/effects/ui-context/events.
- SSE клиент с авто-reconnect и fallback на polling.
- Базовый role-gated UI (streamer/moderator/viewer).

**Критерий готовности:**
- Пользователь может смотреть стрим, голосовать и видеть live-изменения в одном интерфейсе.

### Sprint C — PWA + Mobile-first polish (1–2 недели)
**Цель:** удобство на телефоне и установка как приложения.

- Manifest + service worker (next-pwa/Workbox).
- Offline shell и стратегии кеша по типам endpoint’ов.
- Mobile-first UX: sticky action bar, компактная таблица, touch-first взаимодействия.
- Эффекты: смена лидера, крупный вклад, скорое завершение.

**Критерий готовности:**
- Приложение устанавливается на мобильные устройства;
- основные пользовательские сценарии комфортны на экранах 360/390.

### Sprint D — Twitch integration + MVP release hardening (1–2 недели)
**Цель:** довести MVP до релизного состояния на 1–N каналов.

- OAuth Twitch end-to-end.
- Channel Points интеграция (или production-ready adapter + fallback режим).
- Наблюдаемость: метрики/алерты, расширенный audit, аварийные регламенты.
- Нагрузочный smoke и pre-release checklist.

**Критерий готовности:**
- Можно проводить реальные аукционы на боевом канале с мониторингом и понятной поддержкой.

### Итого до MVP финала
Оценка: **5–8 недель** (в зависимости от размера команды и глубины Twitch integration).
